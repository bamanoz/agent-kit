## Агентская обвязка agent-kit

Этот блок управляется `agent-kit` {{KIT_VERSION}} и обновляется повторной
установкой. Проектные правила пишите вне блока: при конфликте они имеют
приоритет над общими правилами ниже.

## Project Memory

Проект использует два слоя памяти с разными ролями (`ADR-0001`):

- `project-memory/` в Git является версионируемым источником истины по
  baseline, ревизиям архитектуры `ARCH-*`, решениям `ADR-*`, существенным
  изменениям `CHG-*`, контрактам и открытым вопросам `OQ-*`;
- локальный MCP `mempalace` хранит причины решений, историю, рабочие выводы,
  блокеры и ссылки на Git-артефакты. Он не является точной спецификацией.

Приоритет источников при расхождении:

1. код, тесты и машинные контракты определяют фактическое поведение;
2. `project-memory/` определяет baseline, архитектуру, решения и контракты;
3. согласованные требования проекта определяют целевое внешнее поведение;
4. Mempalace объясняет причины и историю, но не переопределяет Git.

### Mempalace

- Крыло проекта: `{{WING}}`. Указывай его во всех вызовах `mempalace_*`
  (`wing`) и используй имя агента `opencode` (`added_by`, `agent_name`).
- Используй только локальное хранилище `.mempalace/palace` и backend
  `chroma`. Не подключай внешние backend (`qdrant`, `pgvector` и др.) без
  явного разрешения пользователя.
- Назначение комнат описано в `project-memory/mempalace-rooms.md`.
- Не сохраняй закрытые ключи, пароли, токены, PIN, персональные данные,
  коммерческую тайну и конфиденциальные материалы без явного разрешения
  пользователя.
- Автосохранение выключено. Сохраняй только важные решения, итоги сессий,
  открытые вопросы, настройки окружения и проверенные выводы: краткий
  проверяемый итог с датой, контекстом, ссылками на Git-файлы и
  последствиями, а не сырой диалог или полный diff.
- На просьбу «сохрани в память», «зафиксируй решение» или «сохрани итог в
  Mempalace» используй `mempalace_checkpoint` или `mempalace_diary_write`.
- После существенной настройки, архитектурного решения или большой сессии
  предложи сохранить итог либо сохрани краткий checkpoint сам, если данные не
  чувствительные.
- Не индексируй целиком большие или закрытые каталоги (`.venv*`,
  `.mempalace/`, `node_modules/`, сгенерированные артефакты). Для mining
  используй ограниченный каталог:
  `scripts/mempalace mine <dir> --backend chroma --wing {{WING}} --agent opencode`.
- Поиск из shell: `scripts/mempalace search "<query>" --wing {{WING}}`.
- MCP и CLI запускаются только через `scripts/mempalace-mcp` и
  `scripts/mempalace` (в Windows — одноименные `.cmd`): они задают палату,
  модель эмбеддингов `{{EMBEDDING_MODEL}}`, языки и отключают автосохранение и
  телеметрию. Не вызывай `.venv-mempalace` напрямую.

### Implementation Memory Workflow

- Порядок сессии задан в `project-memory/session-protocol.md`; выполняй его
  перед изменением целевой кодовой базы.
- Перед работой прочитай `project-memory/baseline.yaml`,
  `project-memory/component-map.md`, `project-memory/change-log.md`,
  `project-memory/mempalace-rooms.md`, активные `CHG-*`/ADR и получи из
  Mempalace комнаты `implementation-baseline`,
  `implementation-change-control`, `implementation-open-questions` и комнату
  затронутого компонента.
- Существенное изменение границ компонентов, контрактов, данных, ИБ или
  приемки оформляй новым `CHG-*`, при необходимости новой ревизией `ARCH-*`
  и ADR. Старое решение не удаляй: ставь `SUPERSEDED` и ссылку на замену.
- Проектный, реализационный и эксплуатационный baseline обновляй независимо
  и только после фактического изменения соответствующего уровня.
- После существенной сессии обнови Git-артефакты и сохрани Mempalace
  checkpoint со ссылками на них, выполненными тестами и открытыми блокерами.

## Project Consistency

- Не допускай расхождений между `README.md`, `AGENTS.md`, `opencode.json`,
  скриптами и значениями по умолчанию в коде.
- При изменении структуры каталогов, MCP-конфигурации, точек входа или
  типового workflow в той же задаче обновляй все их описания, примеры команд
  и help-тексты.
- Не описывай отсутствующие каталоги или компоненты как существующие;
  планируемые элементы явно помечай как планы.

## Subagent Reliability

- После каждой делегации проверяй не только статус, но и содержательность
  результата. Пустой ответ, ошибка, обрыв вывода или результат без
  запрошенных выводов не считается завершением задачи.
- Read-only и create-only делегации (с непересекающимися списками новых
  путей) можно запускать параллельно в пределах лимита concurrency.
  Делегации, изменяющие существующие файлы, подчиняются разделу «Subagent
  Workspace Isolation». При сообщении о лимите concurrency или пустом
  результате одной из параллельных делегаций повторяй незавершенные задачи
  последовательно.
- Не продолжай работу, полагаясь на вывод неуспешной делегации. Перезапусти
  задачу с явным требованием вернуть итог и диагностику; если повтор тоже
  неуспешен, выполни анализ сам и сообщи пользователю об ограничении.
- Перед финальным ответом прочитай результаты всех делегаций, от которых
  зависят выводы или изменения.

## Subagent Workspace Isolation

- Запрещено параллельно запускать два и более субагента, **изменяющих
  существующие файлы** в основном workspace: параллельные записи
  перезаписывают друг друга.
- Read-only делегации можно запускать параллельно в любом количестве в
  пределах лимита concurrency.
- **Создание новых файлов** параллельно допустимо, если каждый субагент
  получает явный непересекающийся список новых путей, ни один путь не
  существует заранее и изменять существующие файлы запрещено. Правка общих
  точек регистрации (`.sln`, `.csproj`, манифесты, индексы) считается
  изменением: ее выполняет только главный агент последовательно.
- Если нескольким субагентам нужно параллельно **изменять существующие
  файлы**, выдай каждому изолированный git worktree (в Windows —
  `scripts\agent-worktree`, те же команды):

  ```bash
  scripts/agent-worktree create <task-name>   # .worktrees/<task-name> на ветке agent/<task-name>
  scripts/agent-worktree list                 # список воркспейсов
  scripts/agent-worktree diff <task-name>     # diff ветки к базе
  scripts/agent-worktree merge <task-name>    # merge --no-ff в текущую ветку
  scripts/agent-worktree remove <task-name>   # удаление worktree и ветки
  ```

- В задании write-субагента явно укажи рабочий каталог
  `.worktrees/<task-name>` и запрети изменять файлы вне его.
- Merge выполняет только главный агент, последовательно, по одному worktree:
  чистое основное дерево перед merge, сборка и тесты затронутых систем после
  merge; при конфликте merge останавливается и разрешается вручную с
  приоритетом контрактов и `project-memory/`.
- Один write-субагент без параллельных write-делегаций может работать в
  основном workspace без worktree.
- `.worktrees/` исключен из Git; после merge удаляй worktree через
  `scripts/agent-worktree remove`.
